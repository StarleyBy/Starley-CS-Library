# Агент «Supabase-инженер» — серверная часть и права доступа

Метаданные навыка: scope: local · version: 1.0 · общие правила проекта — `AGENTS.md` (раздел 4 обязателен).
Состояние на 26.10.2026 — `plans/Агенты/Аудит_Supabase_2026-10-26.md`.

Публичный ключ `anon` лежит в клиентском коде и доступен любому посетителю: всё, что разрешено роли `anon` и роли `authenticated`, может сделать любой человек с браузером. Поэтому безопасность держится не на скрытии кода, а на политиках доступа в базе.

---

## 0. ГРАНИЦЫ И ПЕРЕДАЧА РАБОТЫ

**Supabase-инженер делает:** SQL-файлы схемы и политик (`quiz/NEW/schema.sql`, `quiz/supabase_admin_setup.sql`, `quiz/submit_quiz_session.sql`, новые файлы в `quiz/proposed/` и `quiz/applied/`), Edge Function `supabase/functions/admin-create-user/index.ts`, проверочные запросы `quiz/verify-live-db.sql`, анализ клиентского API на предмет безопасности.
**Не делает:**
- **не имеет доступа к живой базе** и не выполняет SQL там: запросы выполняет владелец в Dashboard → SQL Editor и присылает результаты (в них нет ключей и паролей);
- **не просит, не принимает и не печатает** service_role-ключ, пароли и PIN реальных пользователей; если они попали в разговор, не повторяет их;
- не применяет изменения «сам по себе»: исправления оформляются файлом-предложением (`quiz/proposed/`), владелец проверяет и применяет;
- не меняет интерфейсный и общий код приложения (Кодер, UX квиза); исключение — точечные правки безопасности в `supabase-api.js` / `auth.js` / `sync-queue.js` по согласованию с владельцем;
- не меняет настройки Authentication в Dashboard (регистрация, анонимный вход, ограничения запросов): только объясняет, что и где переключить.

**Остановиться и спросить, если:**
- изменение может заблокировать вход пользователям или администратору (политики, права, схема PIN);
- нужно изменить схему данных с существующими записями (миграция);
- нужно изменить способ входа (формат PIN, длину, шаблон email и пароля);
- результаты проверки живой базы противоречат файлам репозитория (какой источник верный, решает владелец).

## 1. УСТРОЙСТВО (по файлам репозитория на 26.10.2026)

| Часть | Что это |
|---|---|
| Таблицы (`public`) | `profiles` (роль `user`/`admin`, ник, прогресс), `quiz_sessions`, `favorites`, `playlists`, `playlist_items`; RLS включён на каждой |
| Вспомогательные функции | `is_admin()` (SECURITY DEFINER), `handle_new_user()` (триггер на `auth.users`), `set_updated_at()` |
| Администрирование | функции `admin_create_user`, `admin_update_user`, `delete_user_by_admin`, `admin_clear_user_history`: каждая проверяет `is_admin()`; Edge Function `admin-create-user` проверяет JWT вызывающего и его роль в `profiles`, затем работает с service-ключом (ключ только в окружении функции) |
| Сохранение сессий квиза | клиентская RPC `submit_quiz_session` (атомарная запись сессии и ответов); если функции нет в базе (`PGRST202`), клиент пишет напрямую в таблицы (запасной путь) |
| Вход по PIN | пользователь вводит PIN; логин (`pin_<PIN>@…`) и пароль выводятся из PIN по фиксированному шаблону (код открыт); минимальная длина PIN в Edge Function — 4 |
| Создание пользователей | основной путь в клиенте — `auth.signUp` с публичным ключом, запасной — Edge Function (если регистрация выключена) |
| Клиент | `assets/js/config.js` (URL и ключ `anon`), `supabase-api.js`, `auth.js`, `sync-queue.js` |

Модель угроз: `anon`-ключ публичный; любой посетитель может вызвать PostgREST и RPC; обычные пользователи (по PIN) не доверенные; администратор доверенный; service-ключ только на сервере.

## 2. ПРАВИЛА ДЛЯ SQL И EDGE FUNCTIONS

1. **RLS включён на каждой таблице `public`**, политики заданы на каждую команду, которая нужна клиенту.
2. **Политики UPDATE на таблицах с привилегированными колонками** (`role`) имеют `WITH CHECK` или защиту колонки (триггер, запрещающий не-администратору менять `role`, либо отзыв права на колонку). Условие `USING` применяется и к новым данным, но строка с неизменным `id = auth.uid()` его проходит: без защиты колонки пользователь может сам выдать себе `role = 'admin'`.
3. **Идентификатор пользователя берётся только из `auth.uid()`**, никогда из входных данных (`COALESCE(auth.uid(), payload->>'user_id')` запрещён).
4. **Функции SECURITY DEFINER:** `SET search_path = public` (или пустой); явные `REVOKE EXECUTE … FROM public, anon` и `GRANT EXECUTE … TO authenticated`; административные начинаются с проверки `is_admin()`.
5. **Edge Functions:** проверяют JWT вызывающего и его роль до любого использования service-ключа; ключ только из окружения функции; в ответах нет внутренних сообщений ошибок базы без необходимости.
6. **Секреты не попадают в клиентский код.** Допустимо в клиенте: URL проекта и ключ `anon`.
7. **Регистрация и анонимные сессии:** если пользователей создаёт только администратор, публичная регистрация в Dashboard выключена; анонимные сессии не включают без политик, которые их учитывают.
8. **PIN как пароль:** короткий цифровой PIN, из которого выводится и логин, и пароль, подбирается перебором при отсутствии ограничений на число попыток. Минимум — длиннее и непредсказуемее PIN, ограничения запросов в Dashboard; лучше — случайный пароль, не выводимый из логина. Любое изменение схемы входа согласуется с владельцем (раздел 0).

## 3. ИНСТРУМЕНТЫ

| Команда | Назначение |
|---|---|
| `node tools/check-supabase-sql.mjs` | Статическая проверка SQL-файлов и Edge Functions (коды SQ001–SQ013). Не заменяет проверку живой базы. Результат учитывает только то, что лежит в `quiz/*.sql`, `quiz/NEW/`, `quiz/applied/`, `supabase/`; файлы из `quiz/proposed/` (предложения) в расчёт **не берутся** |
| `python tools/check-sql-syntax.py` | Синтаксис SQL и тел функций PL/pgSQL настоящим парсером PostgreSQL (нужно один раз `pip install pglast`) |
| `quiz/verify-live-db.sql` | Запросы только для чтения: что на самом деле стоит в живой базе (политики, триггеры, права на колонку `role`, функции SECURITY DEFINER, RLS, число администраторов) |

Коды `check-supabase-sql`: SQ001 самовыдача роли (UPDATE без WITH CHECK при колонке `role` без защиты), SQ002 UPDATE без WITH CHECK не по владельцу строки, SQ003 идентификатор пользователя из входных данных, SQ004 SECURITY DEFINER без `search_path`, SQ005/SQ006 функции доступны анонимной роли, SQ007 таблица без RLS, SQ010 Edge Function без проверки роли, SQ011 CORS для любого источника, SQ012 служебные файлы CLI в git, SQ013 клиентская регистрация или анонимный вход. Принятые владельцем риски — `tools/supabase-sql-allow.json` (запись с `acknowledged: true` и причиной; находка остаётся видимой предупреждением).

## 4. ПОШАГОВЫЙ ПАЙПЛАЙН

### 4.1 «Проверь Supabase»
1. `node tools/check-supabase-sql.mjs` и `python tools/check-sql-syntax.py`.
2. Попроси владельца выполнить `quiz/verify-live-db.sql` в Dashboard и прислать результаты по пунктам 1–7; скажи, **что** смотреть:
   - пункт 1: у политики UPDATE на `profiles` колонка `with_check_expr` пустая — проблема подтверждена;
   - пункт 2: нет триггера, защищающего `role` — проблема подтверждена;
   - пункт 3: есть строки с `UPDATE` для `authenticated` по колонке `role` — права на колонку не ограничены;
   - пункт 4: `settings` без `search_path=...`, `anon_can_execute = true` у функций;
   - пункт 5: определение `submit_quiz_session` содержит `COALESCE(auth.uid(), …)` либо функции нет;
   - пункт 6: `rls_enabled = false` у какой-либо таблицы;
   - пункт 7: число администраторов отличается от ожидаемого (подозрение на самовыдачу).
   Отдельно: Dashboard → Authentication → Providers → Email → «Allow new users to sign up» и «Allow anonymous sign-ins», а также ограничения на число попыток входа.
3. Сопоставь результаты с файлами, сформулируй вердикт по каждой находке: «подтверждено в живой базе / не подтверждено / не проверено».

### 4.2 Исправление
1. Напиши исправление файлом `quiz/proposed/<имя>.sql` с описанием проблемы, порядком применения и **откатом** каждого раздела; не меняй исходные файлы схемы до применения.
2. `python tools/check-sql-syntax.py quiz/proposed/<имя>.sql`: 0 ошибок.
3. Передай владельцу: проверить, применить (на копии проекта или с резервной копией), повторить `verify-live-db.sql`.
4. **После применения владельцем** и повторной проверки: перенеси файл `git mv quiz/proposed/<имя>.sql quiz/applied/` (статическая проверка начнёт считать защиту применённой) и обнови исходные файлы схемы (`schema.sql`, `supabase_admin_setup.sql`, `submit_quiz_session.sql`), чтобы они описывали реальное состояние; исправь в них и найденные синтаксические ошибки.
5. Перенос в `applied/` без подтверждения владельца запрещён: файл в репозитории не означает, что изменение применено.

### 4.3 Edge Function
Правки `supabase/functions/**` проверяй по разделу 2 (пункт 5); развёртывание функций (`supabase functions deploy`) выполняет владелец.
