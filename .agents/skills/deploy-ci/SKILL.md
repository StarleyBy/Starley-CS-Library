# Агент «Деплой и CI» — публикация сайта

Метаданные навыка: scope: local · version: 1.0 · общие правила проекта — `AGENTS.md` (раздел 4 обязателен).
Партнёры: «Хранитель репозитория» (коммиты, гигиена, секреты в коде), «Хранитель кэша» (версия кэша после публикации).

Сайт публикуется на GitHub Pages при каждом push в `main`. Всё, что лежит в корне репозитория и не удалено шагом очистки, попадает на публичный сайт.

---

## 0. ГРАНИЦЫ И ПЕРЕДАЧА РАБОТЫ

**Деплой и CI делает:** предлагает и (после решения владельца) вносит правки в `.github/workflows/*.yml`, разбирает упавшие сборки по тексту логов, которые присылает владелец.
**Не делает:**
- **не имеет доступа** к GitHub Actions, секретам и логам: логи присылает владелец (без значений секретов); значения секретов не просит и не печатает;
- не меняет workflow без решения владельца: ошибка в нём может остановить публикацию сайта;
- не коммитит и не пушит без просьбы (это «Хранитель репозитория»);
- не правит код приложения и контент.

**Остановиться и спросить, если правка:** меняет триггеры (`on:`), права (`permissions`), окружение `github-pages`, состав секретов; удаляет шаги, влияющие на публикацию; делает проверки блокирующими или неблокирующими (решение о строгости за владельцем).

---

## 1. УСТРОЙСТВО (по `.github/workflows/jekyll-gh-pages.yml`)

Задача `build` (Ubuntu, Node 22) выполняет по порядку:
1. Checkout.
2. Установка Node и кэш npm.
3. `npm ci` (ставит зависимости, скрипт `prepare` устанавливает локальный хук git: в CI он безвреден).
4. *(после патча `ci-preflight.patch`)* **`node tools/preflight.mjs`** — все проверки проекта (≈ 15 секунд). Если любая «жёсткая» проверка падает, сборка останавливается, сайт не публикуется.
5. Синхронизация картинок с Cloudflare R2 (`node scripts/upload-r2.js`; нужны секреты Actions `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET_NAME`; без них скрипт тихо пропускается, картинок в репозитории нет, так что обычно ничего не грузится).
6. *(после патча `repo-cleanup.patch`)* сборка поискового индекса `node search/generate-search-index.js` (≈ 17 секунд; индекс не хранится в git).
7. Очистка: `rm -rf` файлов и папок разработки (в том числе `tools`, `tests`, `scripts`, `supabase`, `scratch`, `plans`, `.agents`, `AGENTS.md`).
8. Выгрузка артефакта (`path: .`).

Задача `deploy` публикует артефакт на GitHub Pages.

Порядок важен: проверки и сборка индекса идут **до** очистки (после неё `tools` и `scripts` уже удалены). Новые шаги добавляют перед очисткой.

---

## 2. ПРАВИЛА

1. Любой новый шаг, который использует `tools/`, `scripts/`, `tests/` или `search/`, стоит **до** шага очистки.
2. Проверка перед публикацией — `node tools/preflight.mjs` (одна команда вместо списка отдельных). «Мягкие» проверки (сейчас `supabase`) показываются как WARN и публикацию не блокируют.
3. Строгость решает владелец: по умолчанию упавшая проверка останавливает публикацию; чтобы показывать результат, но не блокировать, у шага добавляют `continue-on-error: true`.
4. Секреты Actions — только через `${{ secrets.ИМЯ }}`; в `run:` их значения не печатаются; новые секреты завёл бы владелец.
5. Что должно быть удалено с сайта, указывает шаг очистки; проверка `node tools/check-repo-health.mjs` (G010) сообщает, если папки разработки в него не вошли. Перед расширением строки проверь, что страницы и скрипты приложения не обращаются к удаляемым путям (так проверено для текущего списка).
6. Стабильность: версии действий (`actions/checkout@v4` и т. д.) меняются только по решению владельца.

## 3. РАЗБОР УПАВШЕЙ СБОРКИ

Попроси владельца прислать текст лога упавшего шага (Actions → запуск → шаг; без секретов). По названию шага:

| Упал шаг | Вероятная причина | Что делать |
|---|---|---|
| Run project checks (preflight) | Проверка нашла новый дефект (в логе строка `FAIL` и сводка) | Прочитать сводку, найти проваленную проверку и передать профильному агенту: главы — Валидатор глав; квиз — Квиз-Верификатор; каталог — Каталогизатор; локализация — UX квиза; кэш — Хранитель кэша; репозиторий и секреты — Хранитель репозитория; таблицы — Гайдлайнер |
| Install dependencies | Рассогласование `package.json` и `package-lock.json`, сеть | `npm ci` требует точного соответствия lock-файлу: обновить lock локально |
| Sync media to Cloudflare R2 | Нет или неверны секреты, ошибка сети, ошибка конкретного файла | Проверить секреты в настройках репозитория (значения не печатать); повторить запуск |
| Build search index | Ошибка в данных, которые читает генератор (битый JSON манифеста или метаданных) | Передать «Каталогизатору» или «Квиз-Верификатору»; локально воспроизводится командой `npm run build:search` |
| Upload artifact / Deploy | Сбой Pages, превышен размер, права | Проверить настройки Pages и размер публикуемых файлов; повторить запуск |

Если сайт не обновился, а сборка зелёная: у пользователей может держаться старая копия оболочки PWA (см. «Хранитель кэша»: изменился ли `sw.js`).

Откат публикации: в Actions повторно запустить последний удачный запуск либо отменить проблемный коммит новым коммитом (`git revert`, только по просьбе владельца).

## 4. ПОШАГОВЫЙ ПАЙПЛАЙН «ИЗМЕНИТЬ WORKFLOW»

1. Сформулируй изменение и его влияние (что происходит при ошибке нового шага).
2. Подготовь правку как патч (`git diff` по workflow) и проверь на свежем клоне: порядок шагов, существование путей, время.
3. Передай владельцу: применить (`git apply`), коммит и push выполняет он (или «Хранитель репозитория» по просьбе).
4. После первого запуска попроси результат (лог или статус) и подтверди, что публикация прошла.
