# Аудит серверной части (Supabase) — состояние на 26.10.2026

Статическая проверка файлов репозитория: `quiz/NEW/schema.sql`, `quiz/supabase_admin_setup.sql`, `quiz/submit_quiz_session.sql`, `supabase/functions/admin-create-user/index.ts`, клиентский код (`config.js`, `supabase-api.js`, `auth.js`) и проверка синтаксиса настоящим парсером PostgreSQL. **Доступа к живой базе у меня нет**: всё ниже описывает, как база устроена по файлам. Подтвердить или опровергнуть нужно запросами из `quiz/verify-live-db.sql` (только чтение).

Важно для оценки серьёзности: в базе хранятся прогресс по квизам, избранное, плейлисты и ники; клинических данных пациентов там нет. Но администратор может удалять и создавать пользователей и очищать истории, поэтому самовыдача роли администратора — реальная проблема, а не формальность.

## 1. Что найдено

### 1.1 Любой пользователь может сделать себя администратором (высокая серьёзность, если база соответствует файлам)
Политика `profiles_update_own_or_admin` (и прежняя `profiles_update_own` в `schema.sql`) разрешает пользователю обновлять **свою строку целиком**, и ни `WITH CHECK`, ни защиты колонки `role` нет. Достаточно одного запроса из браузера: `update profiles set role = 'admin' where id = auth.uid()`. После этого он получает права администратора: видит профили и сессии других, удаляет пользователей, очищает истории, создаёт аккаунты.

**Что делает это правдоподобным:** клиентский код создаёт пользователей через публичный `auth.signUp` как основной путь (`supabase-api.js`, строка ≈ 963) и переходит на Edge Function только при отключённой регистрации. Значит, вероятно, в Dashboard включено «Allow new users to sign up»: тогда любой посетитель сайта может завести аккаунт публичным ключом и сразу получить аутентифицированную сессию, то есть цепочка «посетитель → аккаунт → администратор» замкнута. Если регистрация выключена, риск сводится к существующим пользователям (кто знает свой PIN).

### 1.2 `submit_quiz_session`: идентификатор из входных данных и синтаксическая ошибка (высокая)
- Функция `SECURITY DEFINER` берёт `user_id` как `COALESCE(auth.uid(), <значение из переданных данных>)`. Вызов без входа с чужим идентификатором запишет сессию этому пользователю в обход RLS (нужно знать UUID жертвы, так что практический риск ниже, чем в 1.1, но схема неверна).
- В файле `quiz/submit_quiz_session.sql` в теле функции не закрыт блок `BEGIN … EXCEPTION`: парсер PostgreSQL сообщает `syntax error at or near "IF"`. Файл **нельзя выполнить как есть**. Либо в живой базе функция исправлена вручную и отличается от файла, либо её нет (тогда клиент использует запасной путь прямой записи, и приложение работает).
- Нет `SET search_path` (замечание линтера Supabase).

### 1.3 Предсказуемый вход по PIN (средняя)
Логин и пароль выводятся из PIN по фиксированному шаблону, который виден в открытом коде; минимальная длина PIN в Edge Function — 4 знака. Подобрать короткий PIN перебором можно, если нет ограничений на число попыток входа; в сочетании с 1.1 найденный PIN даёт путь к правам администратора. Это вопрос конструкции входа (длина PIN, случайный пароль, ограничения запросов), решение владельца.

### 1.4 Мелкое
- Административные функции (`admin_create_user`, `admin_update_user`, `delete_user_by_admin`, `admin_clear_user_history`) сами проверяют `is_admin()` и отказывают, но выполнение разрешено и анонимной роли (лишняя поверхность): закрывается `REVOKE EXECUTE … FROM anon, public`.
- Прогресс (`level_num`, `current_exp`, `total_exp`, `tier_id`) и начисление `exp_gained` задаёт клиент: пользователь может накрутить себе уровень. Для образовательного приложения это терпимо, но стоит знать.
- `supabase/.temp/cli-latest` (служебный файл Supabase CLI) отслеживается git.

## 2. Что в порядке
- RLS включён на всех пяти таблицах `public`; политики по владельцу строки заданы для избранного, плейлистов, пунктов плейлистов и сессий.
- Все административные функции начинаются с проверки `is_admin()`.
- Edge Function `admin-create-user` корректна: проверяет JWT вызывающего, его роль администратора в `profiles`, допускает только известные роли, работает с service-ключом из окружения функции (ключа в репозитории нет).
- В клиентском коде только URL проекта и ключ `anon` (JWT с ролью `anon`): так и должно быть.
- Синтаксис остальных SQL-файлов и функций (`schema.sql`, `supabase_admin_setup.sql`) корректен.

1. Выполнить `quiz/verify-live-db.sql` в Dashboard → SQL Editor и прислать результаты (пункты 1–7); заодно посмотреть в Dashboard → Authentication → Providers: включена ли регистрация новых пользователей и анонимный вход.
2. Если пункт 1 подтверждается: применить раздел 1 из `quiz/proposed/hardening-2026-10.sql` (триггер) на копии проекта или после резервной копии. Это самое важное и самое безобидное изменение.
3. Если регистрация включена, а пользователей создаёте только вы: выключить её (клиент автоматически перейдёт на Edge Function).
4. Разделы 2 и 3 предложения: после проверки определения `submit_quiz_session` в живой базе (пункт 5).
5. Решить вопрос длины и схемы PIN.
6. После применения: повторить `verify-live-db.sql`, перенести файл в `quiz/applied/` (`git mv`), привести исходные SQL-файлы к реальному состоянию.
